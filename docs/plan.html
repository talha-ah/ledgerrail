1.0

Repo, tooling & local infra

The skeleton: a monorepo that builds cleanly and a Postgres that survives a restart.

Built
  • pnpm monorepo (packages/*, services/*), shared tsconfig.base.json, pnpm -r build / typecheck / test
  • Docker Compose: Postgres 18, healthcheck, named volume, env via .env + env_file
  • Plain-SQL migrations applied by a small hand-rolled runner — tracking table, ordering, run-once, one transaction each
  • DB layer: memoized getPool(), query(), and a transaction() primitive doing BEGIN / COMMIT / ROLLBACK / release
  • Secrets out of the repo (.env ignored, .env.example committed), lockfile committed
Caught in review
  • Pool anti-pattern. A single pool.connect() client was cached as “the DB” and released by a different function — use-after-release, and every request serialized onto one connection.
  • env_file is not an interpolation source. ${POSTGRES_DB} rendered empty; Compose booted the DB with blank name, user and password.
  • A green test that proved nothing. Volume persistence “passed” while the env was broken — the Postgres image only reads POSTGRES_* when the data directory is empty, so an already-initialized volume masked it.
  • A .env.local holding a real password was one commit away from the repo.
Done
1.1

The Money type

A pure, zero-dependency integer core. No float is reachable from any code path.

Built
  • @ledgerrail/money — a package with no runtime dependencies
  • Money = { amount: bigint, currency } in minor units; money, parseMoney, formatMoney, add, subtract, isNegative
  • Exponent lookup (USD/EUR/GBP/PKR = 2, JPY = 0) rather than a hardcoded 2 decimals
  • Parse and format are pure string ↔ bigint — no parseFloat anywhere
  • Round-trip proven by a fast-check property test over arbitrary bigint
Caught in review
  • 10 ^ exponent is bitwise XOR, not exponentiation — 10 ^ 2 === 8. The scaling math was silently nonsense.
  • parseFloat reintroduced the exact bug the type exists to prevent, and stored a number in a bigint field.
  • Vitest does not type-check. The suite was green while tsc --noEmit was red — esbuild strips types without checking them. Both gates now run.
  • $100 became $10. Padding appended exactly one zero, so parseMoney("100","USD") returned 1000n instead of 10000n. Every happy-path test passed.
  • formatMoney doubled the sign ("--5") and dropped the decimal point below one unit ("05", not "0.05").
Done
1.2

Event-store schema

The ledger becomes event-sourced: an append-only journal whose immutability is guaranteed by the database, not by discipline. Verified against the running Postgres.

Built
  • accounts — account_number text unique, currency char(3), one currency per account
  • events — global_seq bigint identity PK, event_id uuid (gen_random_uuid), event_type, event_version (schema-evolution seam), payload jsonb, unique idempotency_key, created_at
  • balances — projection keyed by account_id PK with an FK to accounts, amount bigint, last_event_seq (the resume cursor)
  • Statement-level trigger rejecting UPDATE, DELETE and TRUNCATE — all three verified rejected against the live DB
  • Hand-rolled plain-SQL migration runner: tracking table, filename ordering, run-once, advisory lock, one transaction per file
Caught in review
  • Two compilers, two dists. A root tsconfig with rootDir: "." swept the whole repo into a second dist, duplicating every package’s build.
  • A stale compiled sibling. Bare node only worked after a build because it resolved a db.js emitted next to source — fresh code, stale output. Fixed by running through tsx.
  • “client password must be a string.” An unset env var reached pg’s SCRAM auth as undefined — a missing config surfacing three frames deep. Argues for fail-fast config.
  • The linter missed the one real bug. A non-Postgres SQL dialect underlined valid syntax while ignoring get_random_uuid (should be gen_).
  • Double BEGIN/COMMIT (runner and file), SERIAL on an append-only journal, and a row-level guard a zero-row DELETE would slip past.
Done
1.3

PostTransaction + the double-entry invariant

Append a balanced transaction and update the projection inside one DB transaction. Then the hard part: enforcing a non-negative balance when balances are derived, not stored truth — the first real concurrency problem.

Layer 1 — done
  • Command takes an injected client (caller owns the transaction) — posts a balanced event + upserts the balance projection atomically
  • Σ = 0 invariant, same-currency + account-exists guards; six-case suite green, happy path asserts balances moved and one event written
  • Hermetic integration harness: Testcontainers Postgres in globalSetup, committed reference accounts, rollback-per-test isolation, container dropped on teardown
Layer 2 — done
  • Account types: system accounts may go negative (that is how money enters a conserved ledger), asset accounts may not
  • Reproduced the lost update — funded 100, two concurrent debits of 80 on separate connections, both committed, balance landed at −60
  • Fixed with SELECT … FOR UPDATE on each debited balance row; the exemption check precedes the lock so the system account isn’t a global serialization point
  • Reproduction kept as a regression test with the assertion inverted: one debit fulfilled, one rejected with Insufficient funds, balance settles at 20 — see ADR 0002
Caught in review
  • A test that asserted nothing, twice. Un-awaited withClient callbacks meant the assertions never ran; and the earlier suite checked return types rather than whether money actually moved.
  • Two silent hangs, same root cause. A thrown query left a client checked out, so pool.end() waited forever — and the real error never printed. Once the lock made one branch reject by design, cleanup had to move into finally.
  • A missing COMMIT deadlocked the suite — two open transactions held row locks neither would release.
  • Explicit seed ids never advanced the sequence, so the first auto-generated id collided with a seeded row.
  • Tests were excluded from type-checking — an exclude in the shared base config is inherited by every package, so tsc silently skipped every test file.
  • An abstraction that made things worse: wrapping connection handling in callbacks added nesting to a test whose subject was transaction boundaries. Flat and explicit won.
Done
1.4

Idempotency keys

A retried command returns the original result — not an error, not a second posting.

Built
  • INSERT … ON CONFLICT (idempotency_key) DO NOTHING RETURNING; zero rows means replay → look the original up and return its ids, skipping the balance updates entirely
  • Holds under true concurrency, not just sequential retries: two simultaneous calls with one key return identical globalSeq/eventId, exactly one event row exists, and money moves once
Caught in review
  • Catching 23505 can’t work inside a transaction — once a statement fails, Postgres aborts the whole transaction and refuses every subsequent query, so the follow-up lookup is impossible without a SAVEPOINT.
  • The immutability trigger rules out the usual trick. ON CONFLICT … DO UPDATE SET x = x RETURNING always returns a row — but UPDATE on events raises. DO NOTHING plus a second SELECT is the only route.
  • Check-then-insert is not a fix — two retries both check, both find nothing, both insert. It’s an optimization on top of the constraint, never a substitute for it.
  • The clever single-statement CTE version is worse. One statement shares one snapshot, so the SELECT branch can miss a row committed during the conflict wait; two statements get a fresh snapshot and don’t.
  • A test that couldn’t catch a double-apply — snapshotting balances after the race proved the retry was a no-op but never that the race itself moved money once.
Done
1.5

Balance projection

Balances derived from events and rebuildable: drop the projection, replay the journal, get identical numbers.

Built
  • applyToBalances(event, client) extracted as the single projection function — the command and the rebuild are two callers of one implementation, and a Kafka consumer becomes the third in Stage 2
  • rebuildBalances deletes the projection, replays the journal in global_seq order, and asserts the double-entry invariant Σ = 0 across all balances
  • The command projects from the persisted row (RETURNING … created_at, payload), not from its in-memory input — so live and replay consume identical bytes
Caught in review
  • Two write paths had already drifted within one checkpoint — the live insert timestamped balances with NOW() while the rebuild used the event’s own timestamp, so a rebuilt table was never quite the original.
  • A cast that lied about the wire format. The stored payload holds amounts as strings; casting it to the command’s input type claimed bigint, so any arithmetic trusting the type would throw at runtime.
  • A self-check that checked nothing — comparing balance row counts before and after a rebuild passes even if every amount is recomputed as zero. Replaced with the Σ = 0 invariant.
Done
1.6

Snapshots + replay

Replay from event zero is O(history). Periodic balance snapshots at a sequence number make rebuild bounded.

Built
  • balance_snapshots keyed (account_id, as_of_event_seq) — history retained, so any snapshot point can be rebuilt from and a bad one can be skipped
  • balancesSnapshot stamps every account with a single global cursor read once from MAX(global_seq); rebuildBalances seeds from the latest snapshot and replays only events beyond it
  • Regression test: two account pairs transacting at different times, rebuilt and compared before/after — guards the cursor semantics that the earlier bug depended on
Caught in review
  • The writer and reader disagreed about what a cursor meant. Snapshots stored a per-account last_event_seq while the rebuild filtered on the global MAX — so every account not at that maximum was silently dropped, its snapshot ignored and its events never replayed.
  • Σ = 0 passed anyway, because the surviving accounts netted to zero on their own. Reproduced with four accounts: two vanished, the invariant stayed green.
  • Seeding used additive upsert semantics copy-pasted from the event projector, where adding a delta is correct. A snapshot amount is absolute; if that branch had ever been reachable it would have doubled every balance.
  • Two suites were byte-identical duplicates of each other, and the snapshot test asserted only that taking a snapshot didn’t disturb balances — never that a snapshot row was written or that the bounded rebuild agreed with a full one.
Done
1.7

Demo script + Stage 1 failure drill

Kill the process mid-transfer and replay a duplicate idempotency key. The invariant must hold: no partial posting, no double-post.

Built
  • pnpm demo — the whole architecture as one runnable narrative: fund, transfer, reject an overdraft, replay a key and get the same event back, snapshot, wipe balances, rebuild to identical numbers. Amounts printed through formatMoney.
  • pnpm drill:crash — a proxy around the injected client hard-kills the process between the event insert and the balance write. The parent then verifies from a fresh connection that no event with that key exists, balances are untouched, and the rebuild still reproduces correct state.
  • Fault injection needed no change to the ledger — wrapping the injected client was enough, which is the dependency-injection decision paying off a third time (testability, then outbox composability, now drills).
Caught in review
  • A drill that proved nothing, twice. First the child ran under bare node and died on module resolution; then the parent didn’t await the child, so the “after” reading happened before anything was attempted. Both produced reassuring, meaningless output — hence asserting the exit code is 137, not merely non-zero.
  • The child re-ran setup and created its own accounts, so the parent was verifying accounts nothing had touched. Identifiers must be passed down, and assertions scoped to them.
  • A third leaked client. connectDB called pool.connect() and never released, so pool.end() hung forever — the demo did all its work correctly and then refused to exit. A health check needs pool.query("SELECT 1"), not a checked-out connection.
Done

2.0

Kafka plumbing

Redpanda and Console in Compose; a smoke script that produces and consumes one keyed message.

Built
  • Lazily-memoized Kafka client; admin/producer/consumer factories that return handles rather than stash module singletons, so several consumer groups can coexist
  • Deterministic wait — a promise resolved from the message handler, raced against a timeout — replacing a fixed sleep: 32ms instead of 1000ms, and it proves delivery rather than assuming it
Caught in review
  • Advertised listeners, twice. The broker told clients to reconnect to an address unreachable from where they were — once for the app, once for Console. Both times the bootstrap succeeded and everything after it failed, which is the signature to recognise.
  • A ! hid a missing env var until it surfaced eight frames deep inside kafkajs as broker at index 0 is invalid "undefined". Kafka broker lists are host:port, never URLs.
  • Throwing inside eachMessage doesn’t skip a message — the offset isn’t committed and it retries forever, blocking the partition. A poison pill built by accident.
Done
2.1

Transactional outbox

The command records the intent to publish in the same transaction as the event, so a crash can never leave one without the other.

Built
  • outbox keyed by event_id, with global_seq denormalised for ordering, an explicit topic and self-describing partition_key, and a nullable published_at — which answers both “sent?” and “stuck how long?”
  • Partial index over unpublished rows only, so it stays small however large the table grows
  • No outbox row on the idempotent-replay path — the intent was already recorded — giving the invariant that an event row exists iff its outbox row does
  • Decision recorded in ADR 0003: one message per transaction keyed transaction:<event_id>, per-account ordering deliberately not bought
Caught in review
  • A foreign key to a non-unique column — REFERENCES events(event_type) cannot work; an FK must point at a unique or primary key.
  • Keying by event type would have meant one partition forever — same key, same hash, same slot: total ordering with zero parallelism.
  • The drill asserted the outbox was globally empty. It passed only because the table was new; one pnpm demo later there were five rows and it would have failed a working drill. Replaced with a before/after delta.
  • The missing semicolon after CREATE TABLE, for the second time.
Done
2.2

The relay

A publisher that claims unpublished outbox rows, produces them to Kafka, and marks them sent — the seam where at-least-once delivery is born.

Built
  • publishBatch(pool, producer, limit) takes its dependencies; main() owns bootstrap, the drain-until-empty loop and lifecycle, so scheduling stays a deployment decision
  • Joins to events for the payload, orders by global_seq, and publishes an envelope carrying event_id, event_type and event_version — everything a consumer needs to dedup, dispatch and upcast
  • Injecting ProducerHandle means the relay is tested against a fake producer with no broker at all: the interesting logic is which rows are picked, in what order, and which get marked
  • Produce-then-mark recorded in ADR 0003 as Decision 5 — the two failure modes are not symmetric, so we choose the recoverable one
Caught in review
  • A test that couldn’t tell “published” from “marked published”. The fake producer captured every message and nothing inspected them — deleting the send call entirely would still have passed.
  • The type parser was registered where the tests never loaded it. First in index.ts, then in db.ts — neither is in the test import graph, so tests decoded BIGINT as string while runtime decoded bigint. A green suite certifying behaviour production didn’t have. Fixed via setupFiles, which runs in the worker, unlike globalSetup.
  • A generic is a cast, not a check. query<Outbox> promised an event_id the SELECT never projected, so the UPDATE matched zero rows and the relay would have republished forever.
  • Publishing the event id instead of the payload; WHERE topic is $1; and an exported relay() nothing ever called — the bootstrap output came from an import side effect.
Done
2.3

Projection behind the log

A consumer calls applyToBalances; the command stops touching balances, and the temporary import is finally deleted.

Built
  • A consumer process projects balances from the log; postTransaction no longer touches the read model at all
  • account_balances — a write-side authoritative balance with posted/pending, updated inside the command’s transaction, is what the overdraft guard locks and reads (ADR 0004)
  • EventEnvelope declared explicitly with wire types — global_seq and created_at as strings, because JSON has no bigint and a Date survives only as ISO text
  • A validation gate as a type predicate, so the compiler refuses to touch a message before it has been checked; rejections are logged, never silently dropped
  • Verified end to end: write side and read side agree after the relay publishes and the consumer catches up
Caught in review
  • The invariant was being enforced against a lagging projection. Moving the projection async silently broke the overdraft guard — it read a table nothing had written yet. An invariant cannot live on an eventually-consistent read model.
  • Two writers doubled every balance. A rebuild and the consumer both applied the same five events, and because projections apply deltas the read side came out at exactly 2×. Deduplication would not have helped — the duplicate was a second author.
  • The wire contract was derived from the table row, so it inherited a bigint and a Date that JSON cannot carry — and an intersection type meant to override them produced never, because & combines constraints rather than replacing them.
  • The type parser was registered where the tests never loaded it, so tests decoded BIGINT as string while runtime decoded bigint. Fixed with setupFiles, which runs inside the worker.
  • Rollback-per-test was dropped for a single committing model — running two isolation models side by side had been quietly making assertions pass by file-ordering luck.
  • A working system looked broken because nothing logged success: the relay published five events silently and never exited, since it disconnected the producer but never ended the pool.
Done
2.4

Inbox & deduplication

At-least-once means duplicates are guaranteed, and += applied twice is wrong money. Correctness moves into our own table rather than the broker.

Built
  • inbox keyed (consumer_group, event_id) — per group, so a second projection isn’t starved of events the first already handled
  • The claim and the effect commit in one transaction; splitting them recreates the dual-write problem one layer down, which is why the inbox must live in the projection’s own database and why an external cache cannot do this job
  • Detection via INSERT … ON CONFLICT DO NOTHING RETURNING — a duplicate yields zero rows instead of raising and aborting the surrounding transaction
  • Bounded by Kafka retention: a message older than the topic’s retention can never be redelivered, so its inbox row can be pruned. Recorded in ADR 0005, along with the read-side foreign-key decision and its revisit condition.
Caught in review
  • An order-dependent test that looked fixed. A relay assertion compared against every event rather than the publishable ones; it passed only because file ordering happened to cooperate. --sequence.shuffle failed it 4 runs in 6 — and then surfaced a second one immediately.
  • Absolute balance assertions on shared fixtures — each test measured accumulated state rather than its own effect. Cured structurally by creating fresh accounts per test rather than by measuring deltas around the problem.
  • Acquire and release drifted out of scope. Moving fixtures into beforeEach took the client checkout with it and left the release in afterAll, so three of four clients leaked and pool.end() hung the suite.
  • The kept foreign key immediately rejected a synthetic test fixture — pushing the test toward a real event row, which is the constraint doing exactly what it was retained for.
Done
2.5

Dead letter queue

A message that can never be processed must stop blocking everything behind it — without becoming silent data loss.

Built
  • dead_letters keyed by delivery position (consumer_group, topic, partition, kafka_offset) — the only identity every message has, since a malformed one may carry no event_id; re-recording a redelivery is therefore one row, not two
  • A quarantine table takes what it cannot validate: no foreign key to events, event_id as TEXT, raw as BYTEA. Anything strict enough to reject bad input would fail inside the recovery path
  • An error taxonomy rather than a catch: an explicit PermanentError plus SQLSTATE classes 22 and 23; everything unrecognised is transient and rethrows. No retry budget — a budget would drain the topic into this table during a thirty-second outage (ADR 0006)
  • Decoding moved out of the Kafka layer into the wrapper, because a throw at that level escapes past the handler — so unparseable JSON could never have been quarantined by the thing meant to quarantine it
  • A dead letter never claims the inbox: the two tables mean “not applied, needs a person” and “applied”. Redrive replays through the same handler, so the inbox is what keeps it single-apply
  • last_event_seq moves with GREATEST, since a redrive applies an older event after newer ones have landed — the amounts commute, the cursor does not
  • pnpm drill:poison — a throwaway single-partition topic, a poison message, a good one behind it, and an assertion on the group’s committed offset read back from the broker. The property is that the cursor moved past the poison message; every unit test can only prove the precondition
Caught in review
  • An unqualified column inside ON CONFLICT DO UPDATE is ambiguous. Two rows are in scope — the existing one and excluded — and Postgres refuses to guess. Nine tests failed with an error about none of the things they were testing, because every path routes through one insert.
  • A quarantine table that can reject its input cannot do its job. Keeping event_id as UUID meant a message carrying a non-UUID id raised 22P02 from inside the catch block — no row, no log line, and the partition blocked forever on precisely the message the DLQ exists to release. TEXT does not handle that error better; it makes it unrepresentable.
  • A three-s typo the compiler had no way to catch. messsage_key in the row interface while the table and both queries said message_key — internally consistent, so tsc was green, and pg does not check a generic against the SELECT. Every redriven message silently carried key: undefined. The same shape as 2.2’s a generic is a cast, not a check.
  • Two tests asserting opposite contracts, side by side. The old “skips messages that fail validation, without throwing” survived next to its replacement — and the contract it described is the silent data-loss path this checkpoint existed to remove.
  • Both deliberate decisions were held in place by nothing. The TEXT column and the transient rethrow in redrive could each be reverted with the suite staying green. A choice with no test is a comment.
  • The redrive counted a transient failure as “permanently broken” — ignoring the taxonomy built one file away, and reporting fifty dead messages when the truth was one dead dependency.
Done
2.6

Schema evolution

A v2 event alongside v1, and a consumer that must handle both — what event_version was reserved for since 1.2.

Built
  • v2 carries currency per leg rather than once per transaction — a change the multi-currency ledger actually needs, and deliberately breaking: an additive optional field would have let the version machinery be skipped entirely
  • Reconciliation by upcasting at read time, not by branching in the projector or dispatching per version. applyToBalances is where money moves, so the number of routes through it stays at one permanently — adding v3 adds a pure function, not a path (ADR 0007)
  • The upcast is the first line of the projector, not a call at each of the three read boundaries. The rebuild is the caller that would be forgotten, because nothing in production exercises it
  • v1ToV2 copies the transaction currency onto every leg — exact rather than invented, because the command always rejected legs of a differing currency. An upcast that has to invent a value is a warning sign
  • Two switches that cannot drift: one turns a number into the version union or throws, the other is exhaustive over the union and ends in assertNever. Adding a version fails to compile until both are handled
  • An unknown version is a dead letter, not a block and not a drop — a message from the future is permanent for this build, so 2.5’s redrive is the recovery path once the consumer is upgraded. Readers deploy before writers
  • Proof: a rebuild across a journal holding both versions reproduces the live projection row for row. It can only pass if the rebuild upcasts too
  • The relay needed no changes at all — it carries event_version through and never interprets it, which is the 2.3 envelope decision paying off
Caught in review
  • An intersection narrowed the type it was meant to widen. event_version was left out of the envelope’s Omit list, so (1 | 2) & number resolved back to 1 | 2 — the wire type went on promising a known version while the gate deliberately accepted any number. Same mechanic as 2.3’s never: & combines constraints, it does not replace them.
  • The fix that changed nothing. Adding the field to the Omit and then re-declaring it as EventVersion restructured the type and left the claim identical. A type is only widened when the wider type actually lands.
  • A fixture query with three placeholders and two parameters — and behind it, an assertion still expecting the amounts from an earlier draft. Two different amounts, not two identical ones: identical legs cannot distinguish “both events applied” from “one applied twice”.
  • The relay test asserted the version the command emits, and correctly failed the moment the command emitted v2 — then earned its keep by growing an assertion that the per-leg currency actually reaches the wire, which is the one thing the projection tests cannot see once the upcast has flattened it.
  • Never assert against the constant under test. toBe(LATEST_EVENT_VERSION) would have stayed green through the entire checkpoint and reported nothing.
Done
2.7

Stage 2 drills

Kill the relay mid-publish; poison a message into the DLQ; lose Raft quorum by killing 2 of 3 brokers; pause a consumer and watch lag build, then catch up.

Built
  • drill:relay — a producer that succeeds and then hard-kills the process before the outbox row is marked. Two deliveries of one event, one movement of money: at-least-once (ADR 0003) and the inbox (ADR 0005) demonstrated together, in two log lines — applied …/2@0 then skipped duplicate …/2@1
  • drill:lag — lag 0 → 5 → 0 with the projection visibly stale in between. The group’s cursor is seeded with admin.setOffsets rather than a warm-up message, which is the same tool you would use to rewind a group and rebuild a projection
  • drill:quorum — two of three brokers stopped, the cluster asked about itself, three transactions committed anyway, the outbox holding all three, and the relay draining them on recovery. The outage degraded to lag, not to lost or refused writes (ADR 0008)
  • A three-broker Redpanda cluster with RF=3, each broker advertising its own address, and a client that bootstraps from all three — because a single seed makes killing that broker a connection error rather than an observation about quorum
  • The poison drill landed early, in 2.5: drill:poison already proves the committed offset moves past a quarantined message while the message behind it applies
Caught in review
  • Every broker advertised the same hostname, and it did not exist. The rewritten services kept redpanda from the single-node version in both --advertise-kafka-addr and --advertise-rpc-addr. The RPC one is how brokers find each other for Raft, so the cluster could never have formed. Third time advertised listeners have bitten this project, same signature every time.
  • The compose file did not parse at all — three brokers mounting volumes the volumes: block never declared, a console still depending on a service that had been commented out, and redpand-2 missing its a in every --seeds line. docker compose config answers this in one second and was not run.
  • A drill that passed every assertion and never exited. Teardown lived in catch, so the success path skipped it entirely — and a missing log line has two causes, hung or never ran, which look identical and lead to opposite fixes.
  • A fresh consumer group re-applied the whole retained log, silently doubling the balances of every previous run’s accounts while this run’s assertions stayed green, because they were scoped to accounts the corruption never touched.
  • Lag reported zero for a group that had no cursors at all — a sum over an empty list satisfies any threshold, so the assertion establishing the precondition passed precisely when the precondition was absent. Same shape as 1.6’s invariant satisfied by a subset.
  • A warm-up message cannot seed three partitions: a consumer commits offsets only for partitions it has read from, and lag against a partition with no cursor is undefined rather than zero.
  • The drill’s headline claim was assert(true, …) — the one statement the whole exercise existed to make was the only one that could not fail. Replaced with a count read back from events.
  • A catch that swallowed every error made “the publish failed” pass for a Postgres error or a typo just as happily as for a broker outage.
Done

Decisions on the record

the questions an interviewer digs into
DecisionCallReasoning & accepted tradeoff
Write unitTransaction, not accountOne balanced event carries all legs, so the double-entry invariant is checkable inside a single event and a single DB transaction. Defers per-account ordering to the Kafka partition key in Stage 2 rather than paying for cross-stream consistency on day one.
Posting shapeSigned minor unitsA leg carries a signed amount and the invariant is Σ = 0 — one unmissable check, and applying to a balance is += with no branch. Explicit debit/credit needs a conditional whose direction depends on account type, which is where ledger bugs live. Tradeoff: storing the effect on the balance, not accounting vocabulary, so the debit/credit label is derived at presentation time from sign plus account type.
Amount storageBIGINT263 minor units (~9.2×1018) is far beyond anything this system handles, and it maps cleanly onto JS bigint. NUMERIC is arbitrary precision but variable-length and slower — the escape hatch for hyperinflationary currencies or huge aggregate positions.
MoneyInteger minor units in bigintFloats cannot represent most decimals exactly, so money would silently appear and disappear. Exponent lookup rather than a hardcoded 2 because JPY has none.
Money placementA package, not a servicePure domain logic with zero infrastructure dependencies. Services depend on packages; the domain core never depends on infrastructure — which is also why it is the easiest code in the project to test exhaustively.
MigrationsPlain SQL, own runnerWriting the DDL by hand keeps the schema fully legible and teaches the SQL underneath the tool; the runner is only a tracking table, ordering, run-once and a transaction per file. Gives up auto-generated down migrations — which matters less than it sounds, because production practice is forward-only. Revisit a tool once the schema stabilizes.
Buildpnpm -r, one build nowRecursive scripts run in dependency order, so one command builds everything today and each package already owns its own build script for the day a team takes it over. Avoids TS project-references ceremony for a solo build.
Test gatesType-check and testEsbuild-based runners transpile without checking types, so a green suite and a green compiler are orthogonal signals. Both must pass before anything counts as done.
ImmutabilityTrigger, statement-levelAppend-only is a storage-layer guarantee, not a convention — even a buggy service cannot rewrite history. Statement-level so a zero-row DELETE still raises, and covering TRUNCATE, which bypasses DELETE triggers.

Field notes

things to know · grows as we build

Postgres & migrations

“How do you roll back a migration?” You usually don’t. Production practice is forward-only: write a new migration that fixes forward. A down that drops a column is a data-loss event, and rolling back against live writes is often worse than the bug.
How do you make a Postgres-backed service resilient? Bound every wait, make every retry safe, and put invariants where they can’t be bypassed. Timeouts — statement_timeout, lock_timeout, idle_in_transaction_session_timeout; none are on by default, and an unbounded wait is an outage while a fast failure is retryable. Connections — backends are processes, not threads, so the pool’s max is your concurrency limit and exhaustion starves unrelated work; release in finally, and reach for PgBouncer at scale knowing transaction-mode pooling breaks session state. Transactions — keep them short, never do network I/O inside one, lock in deterministic order, and owe retries if you choose SERIALIZABLE. Retries — assume duplicate delivery, use UNIQUE + ON CONFLICT, back off with jitter, and retry only transient errors (40001, 40P01) — a constraint violation never succeeds on retry. Migrations — forward-only, CREATE INDEX CONCURRENTLY, and a lock_timeout, because a blocked ALTER TABLE queues every reader behind it. Constraints in the database — anything enforced only in application code is enforced only where you remembered to. And never enforce an invariant against a replica or an async projection: both are statements about the past.
Why can’t you edit a migration that has already run? Runners track by filename, not content — so an edited file is skipped forever on any database that already recorded it, and its schema silently diverges from the file. Worse, you can’t fix it forward: an ALTER TABLE that repairs the drifted database fails on a fresh one, because the edited file already creates that column. The only consistent state is to recreate the drifted database. A throwaway test container hides this completely, since it is always built from current files.
Postgres has transactional DDL — most databases don’t. You can wrap CREATE TABLE and CREATE TRIGGER in a transaction and have the whole thing roll back on failure. MySQL auto-commits DDL, so a mid-migration failure strands you with a half-applied schema.
Advisory locks stop instances racing to migrate. pg_advisory_lock serializes the run when N services boot at once. It is session-scoped, so lock and unlock must run on the same connection. Better still: run migrations as a deploy step, not at app boot.
Don’t wrap the transaction twice. If the runner wraps each file in BEGIN/COMMIT, the SQL file must not also contain them. The file’s inner COMMIT closes the runner’s transaction early, so the “record this migration” insert lands outside it — and apply-and-record is no longer atomic.
“JSON or JSONB?” Almost always JSONB. JSON keeps the raw text and re-parses on every access; JSONB is parsed binary — indexable with GIN and much faster. Choose JSON only when you need byte-exact round-tripping of whitespace and key order.
SERIAL is a 4-byte int — and legacy. Ceiling ~2.1 billion, which an append-only event journal can reach. Prefer BIGINT GENERATED ALWAYS AS IDENTITY: SQL-standard, and it avoids SERIAL’s sequence-ownership and permission quirks.
Statement-level triggers guard better than row-level ones. A FOR EACH ROW guard never fires on DELETE ... WHERE false — zero rows, zero invocations, statement succeeds. FOR EACH STATEMENT fires once regardless of row count. And TRUNCATE bypasses DELETE triggers entirely, so an immutability guard must name it explicitly.
In Postgres, VARCHAR(n) and TEXT are the same thing. Identical storage and performance; the length is a constraint, not an optimization. VARCHAR(255) is a MySQL habit. Prefer TEXT plus an explicit CHECK when a bound genuinely matters.
The linter is not the authority — the database is. A non-Postgres SQL dialect in the editor will underline valid syntax (GENERATED ALWAYS AS IDENTITY, EXECUTE FUNCTION, $$) while missing real errors like a misspelled function name. Run it against Postgres before believing either verdict.
node-postgres returns BIGINT/NUMERIC as strings. The driver won’t risk precision loss past 253, so a BIGINT column comes back as "1", not a number. Fine to hand straight back into another query; wrap in BigInt(...) before doing any arithmetic on it.
The Postgres image reads POSTGRES_* only when the data directory is empty. An already-initialized volume silently ignores changed credentials or database name — which is how a broken config hides behind a passing test.

Money & correctness

Never represent money as a float. 0.1 + 0.2 === 0.30000000000000004. In a ledger that rounding error means money silently appears or disappears. Store integer minor units.
Currency exponents differ. JPY has 0 decimal places, most currencies 2, Bahraini dinar 3. Hardcoding ÷100 breaks the first time you add JPY.
bigint can’t be JSON-serialized. JSON.stringify throws on it, and JSON numbers lose precision past 253 — so amounts cross a serialization boundary as strings, never numbers.
In JavaScript ^ is bitwise XOR, not exponentiation. 10 ^ 2 === 8. Power is **. This one compiles, runs, and quietly returns nonsense.
The lost update — why a read-then-check guard doesn’t guard. Read balance → check it covers the debit → write is a race. Two concurrent transfers both read 100, both approve an 80 debit, both commit, and the account lands at −60. Reproduced with two connections, each committing. Fixes: SELECT … FOR UPDATE (second txn blocks, re-reads, rejects — but serializes hot accounts), an atomic conditional UPDATE … WHERE amount + delta >= 0 checking rowCount (no read-write window at all), or SERIALIZABLE plus retry on serialization failure.
A sequence is monotonic, not gapless. Identity values are allocated before a conflict is detected and are never returned, so ON CONFLICT DO NOTHING, rollbacks and crashes all leave holes — an idempotent retry visibly burns a global_seq. Ordering by it is safe; inferring “an event is missing” from a gap is not.
Explicit ids don’t advance a SERIAL sequence. Seed rows with hardcoded ids and the sequence stays where it was — the next auto-generated insert hands out an id that already exists and dies on a duplicate key. Same bug bites after restoring a dump. Fix: SELECT setval(pg_get_serial_sequence('t','id'), (SELECT MAX(id) FROM t)) after seeding.
A leaked client turns an error into a silent hang. pool.end() waits for every checked-out client to come back. Release outside a finally and one thrown query strands a client — the pool never closes, the runner hangs and is killed, and the real error message never prints. Always release in finally.
An uncommitted transaction blocks every other writer. A transaction holds its row locks until COMMIT or ROLLBACK. Forget to end one and any other transaction touching those rows waits — forever. “Idle in transaction” connections are one of the most common real Postgres incidents; the symptom is a hang, not an error. Cleanup at the end of a function body never runs on the failure path — put it in finally.
A row lock lives exactly as long as its transaction. SELECT … FOR UPDATE in autocommit acquires and releases the lock within that one statement, so it protects nothing. Locking only works inside an explicit BEGIN … COMMIT — and a race can only be reproduced across separate connections, since one pg connection processes statements sequentially.
How does money enter a double-entry ledger? Double-entry conserves money — the sum of all balances is always zero — so a positive balance anywhere requires a negative one somewhere. Money enters by debiting a source/system account that is allowed to go negative and crediting a customer (asset) account. So the non-negative rule is per account type, not global: forbid every account from going negative and you can never fund the system.
Debit and credit are not “minus” and “plus”. A debit increases an asset account and decreases a liability. That asymmetry is real accounting and a genuine footgun in code — the argument for storing signed amounts and deriving the debit/credit label for humans at the edge.

Testing

Passing tests and a passing compiler are orthogonal signals. Esbuild-based runners like Vitest strip types without checking them, so a suite can be fully green while tsc --noEmit is red. Gate on both.
Example tests only cover the cases you thought of. A single property-based round-trip test (fast-check) caught sign and padding bugs that six hand-written examples missed. Assert the invariant, not a list of samples.
A global invariant can be satisfied by a subset. A rebuild silently dropped two of four accounts, and the Σ = 0 check still passed — the surviving pair netted to zero on its own. An aggregate assertion proves a property of whatever rows are present; it says nothing about rows that should have been there. Pair every aggregate check with a cardinality check, or compare against a captured before-state.
A green test can encode the bug. Write the assertion after the implementation and you assert whatever the code currently does — which is how parseMoney shipped a test proving $100 was $10.
How do you isolate integration tests against a real database? Two clean strategies. Transaction-rollback per test — run each test inside a transaction and roll it back at the end; nothing is ever committed, so there is nothing to clean up and it is fast. Throwaway database per run — create a fresh database (or schema), migrate, run, drop; heavier but gives real isolation across parallel workers and lets you test commits and cross-transaction behaviour.
Why we dropped rollback-per-test for a single committing model. Rollback-per-test gives isolation by construction and needs no cleanup — which mattered because an append-only trigger makes DELETE/TRUNCATE impossible. But it runs everything on one connection inside one transaction, so it structurally cannot test concurrency, cross-transaction visibility, or anything that depends on a commit — which is most of what this project is about. Every interesting test (overdraft race, idempotency race, relay, snapshot regression) had to abandon it. Worse, running both models side by side was itself a bug source: assertions that didn’t say which world they lived in passed only by file-ordering luck. So: one model. Every test creates its own data and scopes every assertion to the ids it created — never a global COUNT(*). The throwaway container keeps runs from leaking into each other; accumulation within a run is harmless once assertions are scoped. The trade accepted: isolation now comes from discipline rather than construction, paid for by assertions that name their own data.
Sequences are non-transactional — rollback doesn’t reclaim ids. A rolled-back INSERT still consumes the SERIAL/identity value, so seeding rows inside a per-test transaction and rolling back makes ids drift (1,2 → 3,4 → …). Commit stable reference data once, or capture RETURNING id — never hardcode ids you expect a rollback to reset.
A hermetic integration-test setup, end to end. Spin a throwaway database (Testcontainers, or a dedicated _test DB), migrate it once in global setup, drop it in teardown. Seed immutable reference data once (committed, stable ids); wrap each test in a transaction and roll it back so its writes never persist — which requires the code under test to accept an injected client (DI). Keep pure unit tests off the database entirely so they don’t wait on a container.
Don’t weaken an invariant to make tests pass. An append-only trigger that blocks DELETE/TRUNCATE means you can’t wipe tables between tests — that is a feature, and rollback-per-test sidesteps it. Disabling the guard in the test environment means you are testing a different system than the one you ship. Other reach-fors: TRUNCATE ... RESTART IDENTITY CASCADE when a guard permits it, or Testcontainers to spin the dependency up per suite.

Architecture & boundaries

“Why is that a package and not a service?” A package is pure logic you import — no I/O, no lifecycle, never deployed. A service is a process you run that owns infrastructure. Services depend on packages; packages never depend on services.
The dependency rule. Domain core depends on nothing; infrastructure sits at the edges pointing inward. That’s why the most safety-critical code in the system is also the easiest to test exhaustively — no mocks, no containers.
Enforce invariants where they can’t be bypassed. Event immutability is a database trigger, not a code convention — so even a buggy service can’t rewrite history.
“How do you rebuild a projection?” Once a consumer owns a read model, you reset its consumer-group offsets and let it replay — stop the consumer, truncate the table, seek the group to the start, restart. Rebuilding by calling a function instead makes a second writer with its own cursor, and since projections apply deltas (amount += x) rather than absolute values, the two writers silently double every balance. We hit exactly that: the read side came out at precisely 2× the write side because a rebuild and the consumer had both applied the same five events.
Deduplication has to be transactional with the effect it guards. “Mark as processed” and “apply the change” must commit together, or you have the dual-write problem one layer down: mark-first loses the event on a crash, apply-first replays it. So the inbox lives in the same database as the projection — which is why an external store like Redis cannot do this job, however convenient it looks. Key it by (consumer_group, event_id), never event_id alone, or the first group to process an event starves every other group of it.
Foreign keys as an inventory of coupling. Keeping FKs across a boundary you may one day split makes the split enumerable — every constraint crossing the line is a piece of work the database will refuse to let you skip. The cost, for a projection specifically: a foreign key imposes an ordering requirement across partitions, so once the referenced entity is itself created by an event, a consumer can legitimately see the child before the parent and be rejected for being behind rather than for being wrong.
A projection needs exactly one writer. Two processes writing the same read model track two independent cursors — a snapshot sequence and a Kafka offset — over one piece of state, and neither knows what the other applied. No amount of per-consumer deduplication fixes it, because the duplicate isn’t a redelivery; it’s a second author. Ownership is the fix, not idempotency.
Three durability contracts in one system. Events are immutable — the source of truth, append-only, enforced by the database. Projections are rebuildable — delete them and replay the journal to get identical state. Snapshots are disposable — pure optimization, regenerable from events at any time. Knowing which category a table falls into tells you what you’re allowed to do to it, and it is the clearest way to explain what event sourcing actually buys.
A snapshot is a claim about the projection, so the projection must supply its cursor. A snapshot row carries amounts read from the projection and a sequence number saying when those amounts were true. Stamp that number with the journal’s head (MAX(global_seq) FROM events) and you assert the projection had applied everything up to that point — which was harmlessly true while the command wrote balances in its own transaction, and false by default the moment the projection moved behind the log. A rebuild then seeds from the snapshot and replays only events after it, so everything the projection had not yet applied is dropped from every future rebuild, permanently. The fix is one line: stamp MAX(last_event_seq) from the projection, the resume cursor that already exists. A snapshot taken while lagging is then still valid — true amounts at a true, lower cursor. Refusing to snapshot a lagging projection would be the wrong guard, because lag is the normal condition; the only honest refusal is an empty projection, where no cursor exists to record. ADR 0009.
A correct decision can rot when something underneath it moves. Stamping the journal’s head on a snapshot was right in 1.6 — the command wrote the projection synchronously, so the journal’s head and the projection’s watermark were the same number. 2.3 moved the projection behind the log and made them two numbers, and nothing announced that the old code now meant something else. This is the failure mode of an assumption that was never written down: it does not break at the moment it stops being true, it breaks the next time somebody relies on it. Worth asking, whenever a boundary moves: what did the old code know that is no longer the case?

Node & tooling

A missing log line has two causes. The call hung, or the call never happened. They look the same from the outside and lead to completely different fixes, so the diagnostic is to log before each step as well as after — whichever label prints last names the call that is stuck, and if none print, the block never ran. process.getActiveResourcesInfo() then names what is still holding the event loop open (Timeout, TCPSocketWrap, TTYWrap) when the answer is a handle rather than a hang.
An intersection narrows — it does not replace. Omit<T, …> & { field: number } only widens field if field is in the Omit list. Leave it out and you get (1 | 2) & number, which resolves back to 1 | 2 — the wider type silently never lands, and a type meant to describe untrusted input goes on promising a value the input cannot guarantee. The same mechanic produces never when the two sides have no overlap, which at least fails loudly. Watch for the non-fix, too: adding the field to Omit and then re-declaring it with the narrow type restructures everything and changes nothing.
Never assert against the constant under test. expect(published.event_version).toBe(LATEST_EVENT_VERSION) passes forever, whatever the constant becomes — it re-derives the answer instead of stating it. Hardcode the value so that changing the constant breaks something and makes you look. The same applies to any test that computes its expectation with the code under test.
Untyped object literals widen string literals. const x = { currency: "PKR" } infers currency: string, which won’t pass where a Currency union is expected. Give the compiler the target type — annotate (const x: T = …) or … satisfies T — so it checks and narrows instead of widening. satisfies also flags the typo at the definition, not the call site.
Node strips types but doesn’t remap specifiers. Node 24 runs .ts directly, yet ./db.js still has to resolve to a real db.js — it will not fall back to db.ts. If bare node suddenly starts working after a build, you are running fresh source against stale compiled siblings. Run TypeScript through tsx, and never emit beside source.
Fail fast on config. An unset env var became undefined, reached the driver, and surfaced as “SASL: client password must be a string” three frames deep. Validate required config at boot and throw something readable.
Simple vs extended protocol — and why parameterized queries are injection-safe. No params → simple protocol: many statements in one string, but values are literals in the text (never interpolate untrusted input). A params array → extended protocol: values travel in a separate message from the SQL, so injection is structurally impossible — at the cost of one statement per call. That tradeoff is why multi-statement migration files run with no params and app queries always pass params.
Use the pool, don’t pin a client. pool.query() per operation; pool.connect() only for transactions, released in the same scope that acquired it. Caching one checked-out client serializes your whole app onto a single connection.
fileURLToPath(import.meta.url) is the file, not its directory. Wrap it in path.dirname() or every path you build off it is one level too deep — the kind of bug that has a generator and a runner quietly reading from two different folders.
Paths in an extended tsconfig resolve relative to where they’re written. A relative outDir/rootDir in a shared tsconfig.base.json anchors to the base file’s directory, so every package would emit into one shared root dist. Those two are inherently per-package; the base holds only location-independent options.
In a per-package-build monorepo, the root tsconfig must not emit. A root config with rootDir: "." and no include compiles the whole repo into a second dist, duplicating every package’s own build. Make the root inert with files: [] — an empty include: [] instead throws TS18003 (“no inputs found”), because an intentionally empty file list must be declared with files, not matched with globs.
Compose env_file is not an interpolation source. It injects variables into the container; it does not feed ${VAR} in the YAML, which is resolved from the host env or a .env beside the compose file. And environment: overrides env_file:.
If every package declares its own deps, what does pnpm buy you? Declaring is not duplicating: pnpm stores each version once in a content-addressable store and links it into every package, so disk/download cost is paid once. The per-package declaration is the feature — a strict non-flat node_modules forbids phantom dependencies (using a package you never declared, present only via hoisting). Centralize versions with a catalog: in pnpm-workspace.yaml if the repetition grates.
Commit the lockfile, never node_modules. The lockfile is what makes installs deterministic across machines and CI.

Distributed systems — ahead of us

“Why not two-phase commit?” You can’t 2PC across a third-party API — there is no prepare phase to enrol a bank in. SAGA with compensations is the only real option, and the tradeoff you accept is eventual consistency windows.
“What actually stops a write when brokers die?” In Kafka the answer is the durability triad: acks=all alone is not enough, because the in-sync replica set can shrink to just the leader and “all replicas” then means one. RF=3 plus min.insync.replicas=2 plus acks=all is the guarantee — below two in-sync replicas the producer gets NOT_ENOUGH_REPLICAS rather than a false success, so losing two brokers costs write availability instead of silently costing data. Redpanda works differently underneath: every partition is its own Raft group, so an RF=3 partition needs 2 of its 3 members to elect a leader or commit anything at all. Kill two brokers and the write fails on the Raft majority, whatever min.insync.replicas says — it exists there as a Kafka-compatibility knob layered on top, and in v26 it is not exposed as a topic config or a cluster property at all.
A config entry accepted is not a config entry applied. createTopics was passed min.insync.replicas=2 as a configEntry. No error, no warning, and the setting simply is not on the topic — rpk topic describe does not list it under any name. The client will happily send a property the broker has no opinion about. Same shape as the linter is not the authority — the database is: confirm infrastructure state by asking the infrastructure, never by the absence of an exception. And give provisioning scripts a voice, because “already exists” and “created three topics” printing the same nothing is how a partition count — a one-way door — gets decided by accident.
“What does event sourcing actually cost you?” Not the storage — the permanent upcasters. The journal is append-only, so a v1 event written today is still a v1 event during a replay in five years, and whatever translates it runs at read time forever. Adding v3 does not replace v1→v2, it chains v2→v3 on top, and old events pay every hop on every replay. Event sourcing does not remove schema-migration work; it converts a one-time migration into code you maintain indefinitely, in exchange for never rewriting history. Nothing lets you delete v1 support while a v1 event exists — not upcasting, not branching, not a handler per version.
Two versions of an event. Where does the branch go? Three places, and the question is really how many routes reach the money. Upcast at the boundary — one pure function normalises any version, and the projector stays at one code path no matter how many versions exist; the risk is that every reader must pass through it, and the rebuild is the reader nothing exercises. Branch in the projector — nothing is invented and the rebuild gets version handling for free, but there are now N routes into the balance and the older branches stop being exercised by anything except replay. A handler per version — real isolation, except most of a handler is not version-specific, so the shared core gets duplicated or extracted, and extracting it gives you the branch again with indirection. Upcast when the shape changed; reach for a handler when the meaning changed — and at that point it is probably a new event type, not a new version.
An upcast that invents a value is a warning sign. Copying v1’s transaction currency onto every leg is exact, because the command always rejected legs of a differing currency — the information was there, just stored once instead of per leg. When the new shape needs something the old one genuinely never carried, the default you pick becomes load-bearing on every future replay of history that can never be corrected. That is the moment to ask whether it is really a new version or a new event type.
Why is delivery at-least-once and not exactly-once? There is no ordering of “produce to Kafka” and “mark the outbox row published” that avoids both loss and duplication, because Kafka and Postgres cannot commit together. Mark first and a crash loses the message forever; produce first and a crash republishes it. We chose produce-first, so duplicates are guaranteed and absorbing them becomes the consumer’s job — which is the entire justification for an inbox.
“How do you handle duplicates?” Start from “duplicates are certain, not exceptional” — at-least-once delivery guarantees them. Then there are only two moves. Make the operation naturally idempotent: writing an absolute value (SET amount = 500) is repeatable; applying a delta (amount += 100) is not, which is why ledger projections need help. Or make duplicates detectable: a unique constraint on a stable identity, checked with INSERT … ON CONFLICT DO NOTHING so a repeat costs nothing and doesn’t abort the transaction — an idempotency key at the API edge, an inbox row keyed by (consumer_group, event_id) at the consumer. The detection record must commit in the same transaction as the effect. And know the limit: this covers database writes only — an email sent before the commit still goes twice, so effects that leave the transaction need their own idempotency keys carried to the third party.
The dual-write problem. Committing to the database and publishing to a broker cannot be atomic — crash between them and you’ve either lost an event or published a lie. The transactional outbox collapses both into one commit.
At-least-once plus idempotent consumers, over exactly-once. Correctness moves into your own inbox table instead of the broker’s transactional machinery. Simpler to operate, and you can explain exactly where duplicates die.
Partition count is a one-way door. You can increase partitions but never decrease them — and increasing them breaks key-to-partition mapping. Messages for transaction:abc that hashed to partition 2 now hash to partition 5, so every ordering guarantee for existing keys is silently void from that moment. Retention and cleanup policy are operational decisions of the same kind.
Topics are infrastructure, not application startup. If the relay and the consumer both call createTopic, whichever boots first decides the partition count — permanently. Provision topics explicitly (a topics:create script run after docker compose up, or a deploy step) so the decision is deliberate and reviewable in one place, and every process assumes the topic already exists. In production, turn auto-create off too: it silently creates a new topic on a typo’d name, with default partitions, instead of failing loudly.
Three options for a message you can’t handle. Throw — the offset isn’t committed, so it retries forever and blocks the partition. Correct for transient failures, catastrophic for permanent ones. Skip silently — the offset commits and the message vanishes: silent data loss, the worst outcome, because nothing surfaces. Skip loudly — commit the offset but record it: log topic, partition, offset and key, bump a metric, and route the message somewhere it can be inspected. That third one is what a dead letter queue is.
“Why not the conventional DLQ topic?” Producing to a DLQ topic and then committing the offset is the dual write again — crash between them and the poison message is either lost or published twice, and a duplicated dead letter has no key to deduplicate on. A row keyed by (consumer_group, topic, partition, kafka_offset) makes re-recording the same redelivery idempotent: one row, not two. The table also lives in the database that already holds the inbox and the projection, so a redrive is a SELECT and a function call rather than a second consumer with its own group and its own ways to get stuck. What the topic buys that we gave up: fan-out and familiarity — other services can subscribe to failures, and every Kafka operator knows how to inspect a topic without being told where your table is. If that becomes necessary, the outbox pattern already in the system relays the table to a topic without touching the recording path.
A message is dead-lettered. What happens to the offset? It advances — because nothing threw. The dead-letter wrapper catches the permanent failure, records the row and returns normally, so the consumer sees a successful eachMessage and commits past it. That is the entire mechanism: quarantining is just not throwing. Throwing is reserved for transient failures, where the offset is deliberately not committed and the partition blocks until the dependency recovers. Two different things get called “the offset”: a record’s offset is its position in the partition, assigned by the broker when the producer appends it and never changed by any consumer; a group’s committed offset is a bookmark in __consumer_offsets, and every group has its own. And a redrive does not touch Kafka at all — it reads rows from Postgres and calls the handler directly, with no group and no offsets; kafka_offset is only provenance, a record of where the message came from.
Transient and permanent failures need opposite responses. A database outage or a lock timeout will succeed on retry, so throwing is right and a briefly blocked partition is the price of not losing data. Malformed JSON or an unknown event version will never succeed, so retrying is the poison pill. Same exception mechanism, opposite correct behaviour — which is why “catch everything and skip” is as wrong as “let everything throw”.
What does fromBeginning actually do? It only applies when the consumer group has no committed offset. Once a group has a cursor it always resumes from it, regardless of the flag — so fromBeginning: true means “where to start if I’m new”, not “replay everything every run”. To genuinely re-read a topic you use a new group id or reset the offsets.
Offsets, water marks and lag. An offset is a message’s position within a partition, starting at 0. The high water mark is the end of the log — strictly, the highest offset replicated to all in-sync replicas, which is why records can exist on a leader but stay invisible to consumers until replicated. The low water mark is the earliest offset still retained. Lag = high water mark − committed offset: how far behind a group is, and the number you alert on.
Kafka stores consumer offsets in a Kafka topic. __consumer_offsets holds a record keyed by (group, topic, partition) with the committed offset as its value. Its cleanup policy is compact, not delete — compaction keeps only the latest value per key, so the topic remembers every group’s position forever without growing unboundedly. That is also what lets a topic act as a key-value store rather than a stream.
A consumer group is a named cursor, not an owner. Messages don’t belong to groups — the topic is one shared append-only log and each group tracks its own position in it. Ten groups read the same bytes independently. It is precisely the last_event_seq cursor on our balances projection, except the broker stores it instead of us.
What is Raft, and where is it in this stack? Raft is a consensus algorithm: a fixed group of replicas agrees on one ordered log. Exactly one member is leader and takes all writes; an entry is committed only once a majority of the group has it durably, which is what makes a committed entry survive any minority of failures. If the leader dies the survivors elect a replacement — but an election also needs a majority to vote, so below majority there is no leader, no commits and no progress at all. The cluster does not serve stale or divergent data; it refuses to move. That is the consistency/availability trade made mechanical rather than philosophical.

Where it sits differs by broker. In Redpanda every partition is its own Raft group, plus a separate controller group for cluster metadata — so an RF=3 partition needs 2 of its 3 replicas to commit a single produce. Apache Kafka in KRaft mode runs Raft for the controller quorum only; partition data uses leader-and-ISR replication, where acks=all plus min.insync.replicas plays the equivalent role. Same guarantee, different machinery — and worth knowing which one you are describing.

What it looks like from a client: a produce to a partition whose leader was on a dead broker fails with ECONNREFUSED — that alone only proves a machine is gone. The quorum-specific evidence is a produce failing to a leader that is still alive, and the broker answering There is no leader for this topic-partition as we are in the middle of a leadership election.
Failure detection is not instantaneous — and the client doesn’t wait for it. Stopping two of three brokers takes 300ms; the cluster reported itself Healthy: true, Nodes down: [] for about 100ms afterwards, because the survivors must lose their RPC connections before they can declare a peer gone. Fast, but not zero — so any check that reads cluster state immediately after inducing a fault reads the state from before it, and a drill written that way fails on an assertion that was true a tenth of a second earlier. Poll until it notices, and log how long that took: the number is the honest answer to “how quickly does your system know a node is gone?” Meanwhile the producer failed immediately, long before the cluster admitted anything was wrong — a client discovers a dead leader by trying to talk to it, not by being told. The control plane’s knowledge and the data plane’s experience are separate clocks.
A non-zero exit can be the answer, not an error. rpk cluster health exits 10 to mean unhealthy, the way grep exits 1 for “no match” and diff exits 1 for “files differ”. A wrapper that rejects on any non-zero status throws away the verdict it was asked to fetch — and reports it as a crashed command, which sends you looking at the wrong thing entirely. Return the code and the output, and let the caller decide which codes mean failure.
Quorum is a majority, not a count. A Raft cluster stays available while a majority survives. Kill 2 of 3 brokers and writes stall — that’s the consistency/availability line made visible. Majority means ⌊n/2⌋ + 1, so a group of 3 tolerates one failure and a group of 5 tolerates two — and an even size buys nothing, since 4 members also tolerate only one. That is why cluster sizes are odd.
